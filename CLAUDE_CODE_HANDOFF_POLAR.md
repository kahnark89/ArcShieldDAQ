# Claude Code Handoff — Polar Biometric Path

**Project:** ArcShield (CIAER+ capture platform)
**Module scope:** `com.arcshield.app.bio.*`
**Generated:** 2026-05-16 (PM session)
**Reconciles / supersedes:** `CLAUDE_CODE_HANDOFF.md` decision 3,
`CLAUDE_CODE_HANDOFF_INTEGRATION.md` §C2.

---

## Why this document exists

The original handoff (April 2026) built the biometric path around
Pixel Watch 4 + Health Connect with `PolarBiometrics` as a planned
future sibling. Kahn confirmed on 2026-05-16 that:

> Pixel Watch only measures HRV while sleeping with no way to access raw data.
> That's why I chose the Polar wearables for biometrics. Let's omit the
> Pixel Watch 4 logic and replace with the necessary logic to integrate
> the polar hardware.

This is fatal for the fusion trigger, which evaluates HRV at 200 ms
cadence over a rolling 2 s window during an active shift. The
Pixel Watch + Empatica path was removed in the same session and
replaced with Polar-only.

This document records the swap so a future session doesn't reintroduce
the rejected design.

## How `PolarBiometrics` works

```
┌─────────────────────────────────────────────────────────┐
│ Polar H10 / Verity Sense                                │
│         │ BLE                                           │
│         ▼                                               │
│ PolarBleApi (RxJava 3 Flowable<PolarHrData>)            │
│         │ kotlinx-coroutines-rx3 .asFlow()              │
│         ▼                                               │
│ PolarBiometrics                                         │
│   • subscribes to HR stream → hr_bpm + RR-intervals     │
│   • appends RR to 60-beat ring buffer                   │
│   • computes RMSSD = sqrt(mean(Δrr²))                   │
│   • feeds BaselineTracker for z-scores                  │
│   • probes for SKIN_TEMPERATURE; subscribes if present  │
│   • updates StateFlow<BiometricSnapshot>                │
│         │                                               │
│         ▼                                               │
│ FusionEngine (not yet built) collects at 200 ms cadence │
└─────────────────────────────────────────────────────────┘
```

### Polar SDK lifecycle

The SDK is held as a singleton via Hilt. `PolarBleApi.defaultImplementation`
is created at injection time with these features:

- `FEATURE_HR`
- `FEATURE_POLAR_ONLINE_STREAMING`
- `FEATURE_BATTERY_INFO`
- `FEATURE_DEVICE_INFO`

The `PolarBleApiCallback.bleSdkFeatureReady` hook fires once
streaming is ready on the connected device — that's where we
subscribe to HR and skin temp.

### RMSSD computation

Polar's HR stream gives `PolarHrSample(hr: Int, rrsMs: List<Int>, ...)`.
We append every reported RR (typically 1–4 per sample at rest) into a
60-beat ring buffer and compute:

```
RMSSD = sqrt( Σ (rrᵢ - rrᵢ₋₁)² / (n - 1) )
```

`MIN_RR_FOR_RMSSD = 5` — below that we return null so the fusion
engine sees "not yet" instead of noise.

### Skin temp (Verity Sense only)

Skin temperature is wired but best-effort: we call
`api.getAvailableOnlineStreamDataTypes(identifier)`, look for
`SKIN_TEMPERATURE`, and subscribe via `api.startTemperatureStreaming`
if present. H10 won't expose it and the snapshot's `skinTempC` stays
null. If the SDK version doesn't surface `SKIN_TEMPERATURE` at all,
the subscription silently no-ops — no crash.

### Device-model inference

We don't ask the user to declare device type. The Polar SDK reports
the device name on connect; we substring-match `H10` → `POLAR_H10`,
`Verity` → `POLAR_VERITY_SENSE`, else `OTHER`. The tag flows into
`BiometricSnapshot.source_device` so events from each strap are
distinguishable downstream.

## What still needs wiring

`PolarBiometrics` is built and DI-bound, but nothing calls `start()`
yet. To get live snapshots you need:

1. **Device pairing UI.** Add a screen in onboarding (or `ConfigScreen`)
   that uses `api.searchForDevice()` to discover nearby Polar devices
   and lets the operator pick one. Persist the chosen device ID into
   `ConfigStore` under a new key, e.g. `polar_device_id`.

2. **Runtime permission flow.** Android 12+ requires runtime grant of
   `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT`. The pairing screen should
   request them via `ActivityResultContracts.RequestMultiplePermissions`
   before invoking `searchForDevice`.

3. **Lifecycle observer.** Inject `BiometricSource` into `ArcShieldApp`
   (or a `MainActivity`-scoped lifecycle observer) and call:
   - `start(deviceId)` when the app foregrounds *and* a deviceId is
     persisted in `ConfigStore`.
   - `stop()` when the app backgrounds.

   This keeps Polar power consumption sane (the strap battery is small)
   and ensures the connection is established by the time the operator
   starts a shift.

4. **Fusion engine.** Layer 2 (`com.arcshield.app.trigger`) is the
   primary consumer of `biometricSource.snapshots` at 200 ms cadence.
   See `CLAUDE_CODE_HANDOFF_INTEGRATION.md` §"What still needs to be
   built" item 1.

## SDK version note

`polar-ble-sdk = "5.6.0"` is a known-good recent version. The Polar
SDK API has shifted across major versions (4.x used different feature
enum names than 5.x). If the build fails resolving `PolarBleSdkFeature`
or `PolarDeviceDataType.SKIN_TEMPERATURE`, check the JitPack release
page and update both the version and any renamed symbol references in
`PolarBiometrics.kt`. The SDK source is at
`https://github.com/polarofficial/polar-ble-sdk`.

## Why Pixel Watch was rejected (for the record)

This is the rejection rationale captured for any future session that
might be tempted to add Pixel Watch back:

1. **HRV is sleep-only on the Pixel Watch 4.** Health Connect exposes
   `HeartRateVariabilityRmssdRecord` only after sleep sessions. There
   is no API path to live beat-to-beat data during an active shift.
2. **Even sleep HRV is smoothed.** Health Connect's HRV reads are
   aggregated; raw RR intervals are not exposed by any consumer
   wearable on Android (Polar BLE SDK is the only path).
3. **Fitbit Body Response.** Was considered as a corroborator but it
   doesn't fire frequently enough for a real-time trigger, and the
   underlying physiology is opaque.

This isn't a "validation experiment pending" question. It's a hard
hardware/API constraint. Don't re-open it.
